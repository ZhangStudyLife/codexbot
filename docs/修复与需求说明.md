# CodexBot 修复与需求说明

本文记录 CodexBot 当前已经确认的问题、已实现功能、这次修复内容和部署验证方法。

## 1. 项目目标

CodexBot 通过 QQ 开放平台沙箱机器人，把本机 Codex 任务的状态和最终结果通知到 QQ，并允许绑定用户进入某个 Codex 任务持续对话。

当前范围是“单用户、自用、QQ 主动通知和任务对话控制”。机器人只接受已绑定 QQ 用户的操作，凭据保存在 Windows Credential Manager 中，不写入仓库或日志。

## 2. 已确认的问题

### 2.1 长 Hook 被静默丢弃

原先 `src/hooks.rs` 将 Hook JSON 限制为 128 KiB。长 Plan、长工具输出或包含较多上下文时，daemon 会记录：

```text
Hook processing failed: hook payload exceeded 131072 bytes
```

事件在解析和入库前就被丢弃，因此不会生成 QQ 通知。这是“Codex 已完成或失败，但 QQ 没有消息”的确定丢失路径。

### 2.2 失败通知必须以最终失败为准

上游可能先返回 429、503、模型容量不足等中间错误，也可能发生重试。通知策略应以整个回合最终状态为准：只有 turn 最终变成 `failed` 时发送一次失败通知；成功回合发送最终回复。不能因为某个中间错误就重复刷屏。

### 2.3 Plan 展示不一定对应 Stop Hook

Codex UI 中看到的 Plan 展示不等同于一定产生标准 `Stop` Hook。若某次操作没有触发可观测的结束事件，机器人无法凭空补发通知；因此需要区分“Hook 超限丢失”和“没有产生可处理 Hook”两类情况。

### 2.4 QQ 快捷操作依赖消息键盘能力

仅发送文字指令时，用户必须手动输入 `/list`、`/chat` 等命令。快捷按钮需要 QQ 开放平台沙箱、主动消息权限以及机器人消息中的 keyboard/action payload 均配置正确；否则客户端只会显示普通文本。

## 3. 本次修复

文件：`src/hooks.rs`

将：

```rust
pub const HOOK_PAYLOAD_MAX_BYTES: usize = 128 * 1024;
```

调整为：

```rust
pub const HOOK_PAYLOAD_MAX_BYTES: usize = 4 * 1024 * 1024;
```

保留“完整读取后再解析 JSON”的方式，不直接截断字节，避免生成损坏的 JSON。超出 4 MiB 仍会被拒绝，防止无限制读取输入。

## 4. 已实现功能

- `/chat <thread_id>`：进入指定 Codex 任务。
- 当前聊天任务持久化到 SQLite，daemon 重启后可恢复。
- 空闲任务收到普通文字时自动启动新的 turn。
- 运行中的任务收到普通文字时使用 `turn/steer`。
- `/chat exit`：退出当前任务。
- `/chat switch`：切换当前任务。
- 任务列表和任务详情提供进入聊天的快捷按钮。
- 任务完成后自动发送完整回复，并在最后一段附带聊天控制按钮。
- 仅在回合最终失败时发送失败通知，支持任意最终错误信息，而不局限于某一种错误文本。
- QQ 绑定码、单用户授权、凭据保护和消息去重。

## 5. 尚未宣称完成的功能

以下属于后续范围，不应在部署说明中当作现有能力：

- 展示完整的上下文时间线并逐条浏览历史消息。
- 通过 QQ 操作任意本机文件夹或执行任意系统命令。
- 完整替代 Codex 桌面端的所有设置和交互。
- 在没有标准 Codex Hook 的情况下推断并补发 Plan 结果。

其中“全盘权限远程操控”风险很高。若未来实现，必须额外加入明确授权、路径确认、命令审计和紧急停止机制，不能默认开放。

## 6. 部署和生效步骤

源码修改不会自动替换正在运行的 daemon。构建后需要：

1. 使用 Release 构建产物重新安装本地 CodexBot 插件。
2. 重启 Codex，使 Hooks 重新加载。
3. 确认 `/hooks` 中的 codexbot Hooks 已信任。
4. 确认 QQ 机器人仍在沙箱中，且允许主动发送消息。
5. 私聊发送绑定命令，例如 `/bind <绑定码>`。
6. 提交一个短任务和一个会产生长输出的任务，分别验证成功通知与失败通知。

不要把 AppSecret、QQ openid、访问令牌或完整日志上传到 GitHub。

## 7. 验证标准

本次修改已完成以下本地验证：

- `cargo fmt --all --check` 通过。
- Release 全量测试 80/80 通过。
- Release Clippy 在 `-D warnings` 下通过。
- Release 构建通过。

部署后还应人工验证：

- 成功回合收到最终回复。
- 最终失败回合只收到一条失败通知。
- 429、503、模型容量不足等不同错误均能在最终失败时通知。
- 长 Plan 或长工具输出不再出现 `hook payload exceeded 131072 bytes`。
- 重启 daemon 后当前聊天任务仍可恢复。

## 8. 版本建议

Hook 上限修复应作为下一个补丁版本发布（例如 `v0.3.1`）。发布时保留上游 `LeaningLearner/codexbot` 的 MIT License、NOTICE 和代码参考声明，并在 Release Notes 中明确列出本地维护分支的改动。
